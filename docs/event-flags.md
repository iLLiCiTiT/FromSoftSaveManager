# Event flags in FromSoftware saves

Findings on where each game keeps its event flags (bonfires/graces lit, bosses defeated,
NPC progress) and how a flag id maps to a bit. Verified against the live saves on the
development machine (October 2026).

## Common layout (DSR, DS3, Sekiro): SprjEventFlagMan / FrpgEventFlagMan

A flag id is read as decimal digits `G AA B T NNN`:

| part | value | meaning |
|---|---|---|
| G | `(id / 10000000) % 10` | flag group |
| AA, B | `(id / 100000) % 100`, `(id / 10000) % 10` | map area and block (`mAA_0B`) |
| T | `(id / 1000) % 10` | thousands chunk |
| NNN | `id % 1000` | bit in the chunk |

The saved buffer is a sequence of groups in order 0..9. Each group has a fixed number of
map slots; a slot is 0x500 bytes = 10 chunks of 0x80 bytes (1000 flags each).

```
offset = groupBase[G] + slot(AA, B) * 0x500 + T * 0x80 + (NNN >> 5) * 4
value  = (u32le at offset >> (31 - (NNN & 31))) & 1
```

Slot 0 of a group holds flags whose map part is 0; slot `n + 1` belongs to the n-th map
block in the game's sorted world-map list. That list contains blocks a player may never
visit, so slot numbers have gaps.

### Dark Souls III

- Buffer: `CharacterSlot::eventFlags` (0x33e00 bytes, `src/parse/DS3/SaveData.h`).
- Group slots (table at `0x14278b670` in DarkSoulsIII.exe, layout builder FUN_1404c6ad0):
  group 0: 1, groups 1, 2, 5, 6, 7: 33 each.
- Map slots: m30_00 2, m30_01 3, m31_00 4, m32_00 6, m33_00 8, m34_01 10, m35_00 11,
  m37_00 14, m38_00 15, m39_00 16, m40_00 17, m41_00 18, m45_00 19, m50_00 22, m51_00 23,
  m51_01 24.
- Bonfires: regulation `Data0.bdt` BonfireWarpParam (+0 lit flag, +8 text id in
  `FDP_メニューテキスト`). Implemented in the app (World Progress tab).
- NPCs: no param names them; they come from the map event scripts
  (`/event/mAA_BB_00_00.emevd.dcx`, EMEVD version 0xCD, 64-bit; instruction names from
  DarkScript3's `ds3-common.emedf.json`). Every NPC owns a block of 20 global flags
  (group 0, ids 1000-1999). Flags base..base+14 are questline stages, base+15..base+19
  its status; the scripts change the status by clearing all five (Batch Set Event Flags
  off) and setting one, so exactly one is set once the NPC's map has loaded (checked on
  all 43 blocks and all 4 test characters). `common_func.emevd` gives the meanings:
  - 20006002 (entity, flag, range start, range end): when the character dies, clear the
    range and set the flag; maps pass base+18 / base+15..base+19.
  - 20006000 (entity, flag A, flag B, ..., range start, range end, which): when the NPC
    is attacked enough, Set Character Team Type 27 and set A (base+16) or B (base+17);
    20006000, 20006001 and 20006003 treat either as "already hostile". Questline events
    also set base+17 when an NPC turns on the player (Hawkwood at Archdragon Peak,
    Leonhard after Rosaria, Eygon after Irina, Horace at Smouldering Lake, ...).
  - base+15 is set the first time the map's script runs (not when the NPC is met).
  - base+18 is also set by questline events when an NPC leaves for good: Yoel after the
    fifth level he draws out, Emma after the Dancer, Hodrick after the Greatwood, Ludleth
    after the Kiln warp (Fire Keeper event 14005110 sets 14000110), Rosaria when
    Leonhard takes her (event 13505728). So it reads "dead or gone".
  The owner is the character in the same event instance (IF Character Dead/Alive, IF
  Character HP Ratio, Set Character Team Type 27), resolved through the map MSB (MSB3
  enemy part: +0xB0 entity data offset, +0xB8 type data offset; entity id at entity data
  +0, NpcParam id at type data +0xC, talk id at +0x10) to NpcParam +0x8 (name id) and
  `NPC名[_dlc1|_dlc2].fmg`. A block is named by the majority of its characters (Horace
  and Anri share some events). 30 named NPCs; the Shrine Handmaid has two blocks (1195,
  entity 4000715, and 1615, entity 4000716, both at the shrine). Left out: blocks whose
  characters have name id 0 or one missing from the FMG (Painted World and Ringed City
  side characters 1675, 1695, 1715, 1735, 1795, 1840, 1845, 1850, 1895, 1915; the
  Undead Settlement giant 1475 and 1950), and 1415 (Lothric, a boss). Questline stages
  are not named in the game data and are not shown. Implemented in the app (World
  Progress tab, "NPCs"); tables generated by `tools/ds3_flags/gen_flags.py`.

### Sekiro

- Buffer: payload of record 1000 (`RecordId::Event`) after a 0x10 byte header and a u32
  size (0x33e00): bytes `[0x14, 0x14 + 0x33e00)`.
- Same group slot table as DS3 (found in sekiro.exe at file offset 0x298dc80).
- Map slots: m10_00 1, m11_00 2, m11_01 3, m11_02 4, m13_00 7, m15_00 8, m17_00 10,
  m20_00 12, m25_00 13.
- Idols: gameparam BonfireWarpParam (+0 flag, +8 text id in `NTC_メニューテキスト`);
  all 55 lit idols of the test character resolve to names.
- Bosses: GameAreaParam row id + 10000000 is the defeat flag (18 bosses, e.g. 11000800).
  The params carry no boss names, but the row id is also the boss's entity id: the
  event scripts' DisplayBossHealthBar (EMEVD 2003:11, args state, entity, slot, NPC name
  id) names 17 of them (12500840 has no health bar).
- Implemented in the app (World tab of the inventory screen); tables generated by
  `tools/sekiro_flags/gen_flags.py`.
- NPCs (not implemented): the map scripts use the same 20-flag blocks in 1000-1999
  (questline batches of 15), and the DS3 scan reads Sekiro's archives as is, but the
  status part differs: scripts only ever clear pairs like 1255-1256 or 1235-1238 and set
  base+15 / base+16 (e.g. m10_00 event 11005910, an aggression check), with no IF
  Character Dead/Alive in the same event. Which flag means dead has to be worked out per
  NPC (or from a different set of common events) before Sekiro can get an NPC list.

### Dark Souls Remastered

- Buffer: `CharacterSlot::eventFlags` (0x16d00 bytes, `src/parse/DSR/SaveData.h`).
- Groups 0: 1 slot, 1, 5, 6, 7: 18 slots each (group bases 0x0, 0x500, 0x5f00, 0xb900,
  0x11300). This matches the long-standing community layout.
- Map slots: m10_00 1, m10_01 2, m10_02 3, m11_00 4, m12_00 5, m12_01 6, m13_00 7,
  m13_01 8, m13_02 9, m14_00 10, m14_01 11, m15_00 12, m15_01 13, m16_00 14, m17_00 15,
  m18_00 16, m18_01 17 (community list; consistent with the 73-slot buffer size).
- Bosses: the defeat flag is the id of the map script event that calls HandleBossDefeat
  (EMEVD 2003:12) for the boss, e.g. 11810001 Asylum Demon (an event's flag is set when
  it completes). The main bosses' events also set global flags 2-16 (2 Gaping Dragon,
  ..., 16 Asylum Demon); both agree on all 10 test characters. GameAreaParam row id
  + 10000000 is not a defeat flag in DSR. Names come from the boss health bars
  (DisplayBossHealthBar 2003:11, packed s16 slot + s16 NPC name id).
- Bonfires: lit state is not an event flag. RegisterBonfire (EMEVD 2009:03, args flag,
  entity, distance, angle, initial kindle) lists 44 bonfires; its flags (e.g. 11010984,
  8 apart) are clear in every save. The save keeps the bonfires in
  FrpgNetBonfireDb, net data chunk 8 (`src/parse/DSR/BonfireDb.h`): per bonfire entity
  a kindle value, 0 when unlit; the bonfire object's fire effect is 90000 + the level
  bucketed from it. It survives New Game+, so NG+ characters show the previous cycle's
  bonfires as lit.
- Global flags 200-220 are set when the bonfire is first rested at and gate the
  Lordvessel warp list (21 rows of flag, bonfire entity, PlaceName id 2000-2020 at
  0x141a325c0 in DarkSoulsRemastered.exe, FUN_1406ed740). They are cleared in New Game+.
- Implemented in the app (World Progress tab); tables generated by
  `tools/dsr_flags/gen_flags.py` (warp list names for 21 bonfires, community names after
  DSR-Gadget's `Resources/Bonfires.txt` for the rest).
- NPCs: every NPC owns a block of global flags in 1000-1999 (Solaire 1000-1029, Andre
  1320-1339, Vamos 1340-1343, ...), but unlike DS3 the status flags sit at no fixed offset.
  Each map script defines template events that its constructor (event 50) instantiates
  once per NPC with InitializeEvent parameters; the parameter table (event +0x0C count,
  +0x10 offset into the section at header word 9; 0x14 byte entries: instruction index,
  target byte, source byte, length) copies the InitializeEvent arguments after slot and
  event id into the instruction arguments. The `.emeld` file next to each script holds
  the developers' event names (header +0x10 count, +0x14 entries of 12 bytes: event id,
  name offset; UTF-16 strings at +0x2C) and tells the templates apart:
  - `NPC死亡（area）` (entity, range start, range end, flag): when the NPC's HP reaches 0,
    Batch Set Event Flags off over the block, then set the dead flag (Solaire 1005).
    Per-NPC events named `... 死亡（...）` do the same for questline deaths (Solaire
    killed as a sunbro maggot 1011, Oscar hollow 1062, Rhea in the Catacombs 1177/1180,
    Domhnall 1435, Shiva in the Painted World 1608/1609, ...).
  - `NPC敵対（area）` (entity, flag): when the NPC is attacked enough, set the hostile flag
    (Solaire 1004) and change its team. Questline turns use per-NPC `... 敵対` events
    (Rhea hollowed 1181, Lautrec 1578, Patches 1625). `... 敵対でいなくなる` (Frampt and
    Kaathe leaving after being attacked) sets a "gone" flag and is not counted.
  - common.emevd event 770 `免罪イベント` (absolution, Oswald) clears the hostile flags of
    every NPC; the ones no named event sets (Frampt 1646, Kaathe 1675) come from the talk
    scripts and are counted as hostile too.
  So an NPC is dead when a dead flag is set (the block is cleared first, checked on the
  test saves), else hostile when a hostile flag is set, else alive when any flag of its
  block is set (event 50 of common.emevd sets the first flag of most blocks at the
  start of the game). 38 NPCs. Names: the game names few NPCs (`NPC_name_.fmg` is mostly
  bosses), so each block was identified from its developer names and the dialogue of the
  character the events act on: MSB1 enemy part (entity id, model, NpcParam at type data
  +0xC, talk id at +0x10) -> `script/talk/<map>.talkesdbnd.dcx` `t<talk id>.esd` -> the
  `Conversation_.fmg` ids in the script (one 10000-id range per character, e.g.
  29000004 "I'm Andre, of Astora."). Left out: 1240 Gwyndolin and 1690 Priscilla (bosses),
  1140 Anastacia (all her events run when she dies and choose a state for the talk script,
  as she can be revived; none is a death), 1710 Alvina (no death or hostile event).
  "Gone" states (Frampt 1647, Kaathe 1677, Quelana 1292/1296, Ciaran 1865) are not shown.
  A flag other named events also set is a stage, not a hostile flag (1766, Shiva in
  Darkroot). Questline stage of every flag: `docs/dsr-npc-stages.md`.
  Implemented in the app (World Progress tab, "NPCs"); tables generated by
  `tools/dsr_flags/gen_flags.py`.

## Elden Ring

- Region: 0x1bf99f bytes in the character slot, after the storage chest, gestures,
  unlocked regions, ride data, menu profile (0x1008), trophies (0x34), GaItemData
  (8 + 0x1b58 * 16), tutorial data (0x408) and 0x1d unknown bytes.
- Flags live in 1000-flag blocks of 125 bytes; a block's position is its rank in the
  game's block table. Bit order is MSB first (bit 7 of the byte = lowest flag).
- Known positions and the grace/boss lists come from ER-Save-Editor (Apache-2.0,
  github.com/ClayAmore/ER-Save-Editor, `src/db/event_flags.rs`, `graces.rs`, `bosses.rs`):
  314 graces and 157 base-game bosses. On the test save: 35 graces / 7 bosses for an
  early character, 261-297 graces / 120-151 bosses for late-game characters.
- Grace names are also available from regulation BonfireWarpParam + PlaceName.
- Implemented in the app (World Progress tab); tables generated by
  `tools/er_flags/gen_flags.py`.
- NPCs (not implemented): the repo has no reader for Elden Ring's game archives (the
  tables come from ER-Save-Editor). Its scripts are the same EMEVD family as DS3/Sekiro
  (common_func.emevd plus per-map scripts), so the DS3 approach is the place to
  start once the archives (Oodle, as Sekiro) can be read.

## Dark Souls II

DS2 does not use the layout above. Progress is in the SaveDataEvent record (0x21c8 bytes)
of each character's world entry (USER_DATA011..020), typed as `EventData` in
`src/parse/DS2/SaveData.h`. Its writer (FUN_1402e3a70, SaveDataEvent vtable slot 2) is not
obfuscated; it copies four EventManager (`[DAT_1416148f0 + 0x70]`) parts:

- +0x20 EventFlagManager (FUN_1404742c0): 0x000 group 10 (0x4e2 bytes), 0x4e4 a second
  global group (0x4e2 bytes), 0x9c8 42 map slots of 0x19 bytes, 0x11e4 three loaded maps
  (map code + two 0x19 byte groups).
- +0x28 (FUN_14047a1c0): 0xde4 0x400 bytes, the u32 kill count per boss index, plus 0x100
  bytes per loaded map.
- +0x58 EventBonfireManager (FUN_14017e540): 0x1598 u16 bonfire ids (MapObjectBonfireParam
  rows), 0x1798 state bit 0 per bonfire, 0x1898 the rest of the state byte, 0x1998 u64 each.
- +0x38 (FUN_14047af60): 8 u32 at 0x21a8. 0x2198/0x219c are the last rested bonfire's map
  code and id.

Event flags (EventFlagManager, FUN_140474230 get / FUN_1404750b0 set): id = group * 10000 +
bit, bit 0 is the high bit of the group's first byte. Groups are hashed by id; group 10
(100000..109999) is the block at 0x000 (checked: flags 100100 / 100110, set by
FUN_1404747c0, are set on the late-game test character). The second global block is
presumably group 1000 (FUN_1404747c0 walks ids 10000000..10009999), not checked. Map groups
are ((area / 10) * 100 + block) * 100 (m10_10 -> 11000) with + 1 and + 2 only while the map
is loaded (FUN_1404745c0). Which of the 42 slots a map uses comes from an obfuscated map
manager call (thunk_FUN_141b39d4f) and is not known; the slot order is not the order of
SaveDataObj's generator list.

- Bonfires lit: state bit 0 of the bonfire's entry, found by id (verified: 30 of 77 on the
  late-game test character including the last rested bonfire, none on the new one).
  Names: `bonfirename.fmg` by row id. MapObjectBonfireParam +0x10 area map id, +0x23 warp
  list position.
- Bosses: FUN_1401826d0 runs on a boss kill with a BossBattleParam row: it sets the flags
  at +0x10 (map group) and +0x14 (group 10) and adds a kill under the index at +0x18. The
  app reads the +0x14 flag; on the test save the 13 set flags are exactly the 13 indices
  with a kill count at 0xde4. Names: +0x2c/+0x30/+0x34 index a 49 entry boss name FMG
  (archive hash 0xE4F0B417, path unknown); +0x3c is the bonfire by the boss.
- Bonfire levels (0x1898) are 0 for every bonfire on the test save, so what they count is
  not confirmed (probably bonfire intensity).
- Implemented in the app (World Progress tab); tables generated by
  `tools/ds2_flags/gen_flags.py`.
